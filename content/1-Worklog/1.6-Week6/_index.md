### Internship Period

**June 08, 2026 - June 14, 2026**

### Week 6 Objectives

* Write queries to retrieve metrics that reflect system performance and operational status.
* Monitor `CPUUtilization`, `NetworkIn`, and `NetworkOut` metrics through Amazon CloudWatch.
* Set up a centralized dashboard to display important metrics in a single interface.
* Develop the ability to interpret monitoring data in order to identify abnormal behavior and support system optimization.

### Internship Activities

#### 1. Exploring Metrics in Amazon CloudWatch

I continued studying **Amazon CloudWatch** and how it stores and aggregates metrics generated by AWS resources. For the Amazon EC2 instance used in the exercise, the main metrics were:

* **CPUUtilization:** the percentage of allocated CPU capacity currently being used.
* **NetworkIn:** the amount of network data received by the EC2 instance.
* **NetworkOut:** the amount of network data sent by the EC2 instance.

Monitoring these metrics together provides a broader view of the server's processing load and network activity. When a metric increases or decreases unexpectedly, it should be compared with the timing of application activity and other related metrics to help identify the cause.

#### 2. Writing Metric Retrieval Queries

I practiced using the AWS CLI to retrieve metric data from the `AWS/EC2` namespace. The queries required parameters such as the metric name, instance ID, time range, aggregation period, statistic, and AWS Region.

The main command groups reviewed and practiced were:

* Using `aws cloudwatch get-metric-statistics` to retrieve data points for one metric over a specified time range.
* Using `aws cloudwatch get-metric-data` to query multiple metrics or data series in a single operation.
* Filtering data with the `InstanceId` dimension to retrieve metrics for the intended EC2 instance.
* Choosing an appropriate time range and `Period` so that the returned data was meaningful for analysis.
* Comparing `Average`, `Maximum`, or `Sum` statistics according to the purpose of each metric.

For `CPUUtilization`, I used percentage values and reviewed average or maximum statistics. For `NetworkIn` and `NetworkOut`, I examined the total number of bytes transferred during each period to understand the level of network activity.

#### 3. Analyzing Retrieved Metric Data

After running the queries, I reviewed the returned timestamps, metric values, units, and dimension information. The results were compared with the exercise time range to confirm that the query targeted the correct resource and Region.

I also reviewed common causes of unexpected results, such as an incorrect instance ID, an incorrect namespace, a time range with no available data, or a Region that did not match the location of the resource. These checks improved the accuracy of using metrics for monitoring and performance analysis.

#### 4. Setting Up a Centralized CloudWatch Dashboard

I created a **CloudWatch Dashboard** to display the system's key metrics in one centralized interface. The dashboard was organized into widgets appropriate for each data type:

* A widget showing the `CPUUtilization` trend over time.
* A widget comparing `NetworkIn` and `NetworkOut` traffic.
* Time-range and refresh settings appropriate for monitoring needs.
* Clear widget names and layout so that the resource condition could be reviewed quickly.
* A basic validation by generating activity on the resource and observing changes in the charts.

A centralized dashboard reduces the need to switch between service screens, supports visual monitoring, and provides a foundation for configuring alarms in later activities.
